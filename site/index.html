Four attacks, the same answer

Each runs in the demo with a scripted stand-in for the model, made to act compromised.

The invoice says pay someone else

The merchant’s text moves the payment account to attacker.test.near, and the agent obeys.

Refused MerchantNotAllowed

A plain wallet key pays the attacker.

A script holds the agent’s key

It calls the vault directly, skipping the app. The key can only ask.

Refused MerchantNotAllowed

A plain wallet key is the whole balance.

The app asks the wallet for 0.009

The stored payment is 0.008. The contract compares every field of the approval.

Refused ApprovalMismatch

A swapped payment that is also waiting would pass. Only the wallet’s display of the full call catches that.

Eight requests sent together

Eight keys ask for 0.004 each while one payment still waits. The queue holds eight, so the last is refused.

Settled seven Refused one, TooManyPending

A plain wallet key sends all eight.

Where the money sits

The agent never holds a balance. One restricted key lets it ask; the contract decides.

What a deployment needs

  • ToolchainRust 1.93+ (wasm32 target), cargo-near 0.22, Node 22.13+, pnpm 11, Python 3
  • Ownera NEAR account; a wallet that shows full call arguments
  • Fundsone token balance on NEAR Intents
  • Agenta function-call key limited to request_payment
  • Testnetabout 18.5 NEAR; it deploys its own copy of Intents

What it does not protect

  • The owner’s keyStolen, it changes the policy and withdraws.
  • DeliveryA merchant can take payment and not deliver. The limits cap the loss.
  • Intents adminsCan pause, lock, force-transfer the vault’s balance and upgrade Intents.
  • A lost callbackKeeps its slot and day’s reservation until the owner resolves it after ten minutes.
  • Midnight UTCThe cap resets; up to twice it can move across the boundary. Accepted.
